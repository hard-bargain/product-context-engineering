## Section 1: EPIC Overview

### 1.1 Problem Statement

**Context:**
Cross-discipline product teams (strategists, managers, marketers, designers, developers, testers) increasingly work with AI agents throughout the product development lifecycle. However, there's no established methodology for:

1. **Context Structure** - How to organize and maintain context for AI agents
2. **Context Evolution** - How context should evolve across product development phases
3. **Team Collaboration** - How different disciplines contribute to and consume AI context
4. **Context Handoffs** - How context transfers between phases and team members
5. **Quality Assurance** - How to validate that AI context enables effective collaboration

**Current State (Without Methodology):**
- Teams use ad-hoc context management approaches
- Context becomes stale or inconsistent across phases
- Different disciplines reinvent context patterns
- AI effectiveness varies wildly based on context quality
- No systematic approach to context evolution through product lifecycle

**Desired State (With ACE Methodology):**
- Clear patterns for structuring context by phase and discipline
- Context evolves systematically through product lifecycle
- Cross-discipline teams share consistent context practices
- AI agents provide consistent value across all product phases
- Quality metrics for context effectiveness

### 1.2 Solution Approach

Develop **AI Context Engineering (ACE)** methodology using GHM-M:

**Core Concepts:**
- **Context Layers**: Strategic, Tactical, Operational context for different team members
- **Phase Alignment**: Context structure aligned with product development phases (e.g., GHM's 10 phases)
- **Discipline Patterns**: How each discipline (strategy, design, dev, etc.) structures their context
- **Evolution Workflows**: How context grows and refines through product lifecycle
- **Validation Criteria**: Metrics for context quality and AI effectiveness

**Methodology Components:**
- Practitioner journeys for each discipline
- Context patterns and templates
- Workflows for context evolution
- Tools for context validation
- Case studies and examples

**Validation Approach:**
This EPIC documents the development of ACE using GHM-M, serving as VAL-001 to test whether GHM-M works for developing methodologies beyond itself.

## Section 5: Notes & Context

### 5.1 Key Decisions

**Decision Log:**

1. **Focus on cross-discipline teams**
   - Date: 2025-12-26
   - Rationale: Tests if ACE works for diverse practitioners (like GHM-M does)
   - Impact: Need patterns for multiple disciplines

2. **Align with product lifecycle phases**
   - Date: 2025-12-26
   - Rationale: Context needs vary by development phase
   - Impact: Context patterns tied to phase progression

3. **Target v0.4 Foundation (not v1.0)**
   - Date: 2025-12-26
   - Rationale: Goal is validation, not complete methodology
   - Impact: Focus on core patterns, not exhaustive coverage

### 5.2 Dependencies

- Knowledge of cross-discipline team dynamics

**Internal Dependencies:**

### 5.3 Risks & Mitigations

| Risk | Impact | Probability | Mitigation |
|------|--------|-------------|------------|
| ACE too similar to GHM-M | Low validation value | Medium | Focus on context-specific patterns, not just process |
| Too many disciplines | Scope creep | Medium | Limit to 3-4 core disciplines initially |
| Patterns too abstract | Poor practitioner adoption | Medium | Include concrete examples for each pattern |
| GHM-M doesn't fit ACE domain | Validation failure | Low | Document gaps honestly, propose refinements |
